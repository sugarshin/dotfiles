# pr-briefing スキル

コードレビューに着手する**前に**、PR の背景・課題・アプローチを日本語で理解し、そのアプローチが筋が良いかを判断するためのブリーフィングを生成する。

**このスキルはコードレビューではない。** 行単位の指摘・nit・スタイル指摘はスコープ外。目的は「この PR は何を、なぜ、どう解決しようとしているのか」の理解と、「そのアプローチは筋が良いか」の事前判断に限る。

## 引数の処理

`$ARGUMENTS` を解析する:

- **PR URL**（`https://github.com/{owner}/{repo}/pull/{number}`）→ owner/repo と PR 番号を抽出
- **番号のみ** → カレントディレクトリの `git remote get-url origin` から owner/repo を推定。git リポジトリ外なら質問する
- **番号 + owner/repo** → そのまま使用
- **複数 PR** → 1 件ずつ順番に処理し、それぞれ独立したブリーフィングを出力

## Step 1: PR 情報の収集

```bash
gh pr view <number> --repo <owner>/<repo> --json \
  title,body,author,state,url,createdAt,baseRefName,headRefName,\
additions,deletions,changedFiles,labels,commits,closingIssuesReferences,comments,reviews
```

- **description（body）** が背景理解の第一情報源。空または内容が薄い場合は、コミットメッセージの body（根拠が書かれていることが多い）と diff から再構成し、その旨をブリーフィングに明記する
- **closingIssuesReferences** にリンク issue があれば `gh issue view` で本文を取得する。body 中の `#NNNN` 参照も同様
- **既存のレビューコメント・議論**（comments / reviews）があれば目を通す。他レビュアーが既に指摘した懸念は筋の評価のインプットになる
- CI 状態を 1 行で把握: `gh pr checks <number> --repo <owner>/<repo>`（失敗していても中断しない。ブリーフィングに記載するのみ）

### diff の取得

`additions + deletions` で規模を判断する:

- **〜2,000 行程度**: `gh pr diff <number> --repo <owner>/<repo>` で全量取得
- **それ以上**: まず `gh pr diff --name-only` でファイル一覧を把握し、
  `gh api "repos/{owner}/{repo}/pulls/{number}/files" --paginate` で per-file patch を取得。
  生成物（lockfile, snapshot, codegen 出力等）は読み飛ばし、ロジックの中核ファイルを優先して読む。
  読み飛ばしたファイルはブリーフィングの「変更の全体像」に名前だけ挙げる（黙って省略しない）

## Step 2: 周辺コードの文脈収集

筋の良さは diff 単体では判断できない。変更**前**のコードと既存パターンを確認する:

- カレントディレクトリが対象リポジトリ内 → ローカルのコードを Read / Grep で直接読む
- そうでない → `gh api "repos/{owner}/{repo}/contents/{path}?ref={baseRefName}"` で必要なファイルだけ取得する（ローカルパスを探し回らない）

確認する観点（筋の判断に必要な深さだけ。網羅調査はしない）:

1. 変更対象の既存実装は元々どうなっていたか（PR が主張する問題は実際にコードに存在するか）
2. コードベースに同種の問題を解く既存パターンがあるか（この PR はそれに従っているか、独自路線か）
3. 変更箇所に依存している他のコードはあるか（影響範囲）

## Step 3: 背景・課題・アプローチの再構成

収集した情報を日本語で再構成する。ルール:

- **事実と推測を区別する。** description・コミットに明記されていることは事実として、diff や周辺コードから読み取ったことは文末に「（推測）」を付けて書く
- **PR 本文の主張を鵜呑みにしない。** 「〜を修正した」「〜を検証済み」という主張は diff と突き合わせて確認する。主張と実装が食い違う場合はブリーフィングで明示的に指摘する（筋の評価の重要インプット）
- 技術用語・識別子は原語のまま、説明は平易な日本語で書く。英語 description の直訳ではなく「日本人エンジニアが同僚に口頭で説明する」トーンにする

## Step 4: 筋の良さ評価

以下の観点で評価し、4 段階判定を下す:

1. **課題設定の妥当性** — 解こうとしている課題は実在するか。根本原因を突いているか、対症療法か
2. **ソリューションの適切性** — 課題に対して過剰（オーバーエンジニアリング）／過小でないか。もっとシンプルで標準的な解法はないか
3. **既存コードとの整合性** — 既存のパターン・慣習に沿っているか。逸脱している場合、正当な理由があるか
4. **影響範囲とリスク** — 副作用、後方互換性、運用面のリスク。失敗したときの blast radius
5. **検証の十分性** — description の検証記述やテストは、主張を実際に裏付けているか。「Not verified」と明記された範囲は妥当なリスクテイクか

判定は次の 4 段階 + Confidence（High / Medium / Low）:

| 判定 | 意味 |
|---|---|
| ✅ 筋が良い | 課題・解法とも妥当。安心して詳細レビューに進める |
| 🟢 概ね筋が良い | 方向性は正しいが、確認したい点が残る |
| 🟡 懸念あり | アプローチに疑問がある。レビューで議論が必要 |
| 🔴 筋が悪い | 課題設定または解法が不適切。代替案を提示して差し戻し候補 |

判定には必ず根拠を付ける。「懸念あり」以下の場合は、自分ならどう解くかの代替案を 1 つ以上示す。

## Step 5: 出力

チャットに直接、以下のフォーマットで出力する（ファイル保存は求められた場合のみ）:

```markdown
# PR ブリーフィング: {title}

{URL} | {author} | +{additions} / -{deletions}（{changedFiles} files）| CI: {状態}

## ⚡ TL;DR

（3 行以内: 何を・なぜ・どうやって）

## 📖 背景

（この変更が生まれた状況。事実と推測を区別して）

## 🔥 課題

（何が問題だったのか。根本原因が特定されていればそれも）

## 🛠 アプローチ

（どう解決するか。核心となる技術判断を箇条書きで 3〜5 個）

## 📂 変更の全体像

（ファイルをグループ化して役割を 1 行ずつ。読み飛ばした生成物もここに列挙）

## ⚖️ 筋の良さ: {判定}（Confidence: {High/Medium/Low}）

（判定の根拠。主張と実装の食い違いがあればここで指摘。
「懸念あり」以下なら代替案も）

## 👀 レビューで重点的に見るべき点

（詳細コードレビュー時のチェックリスト 3〜7 個。
「筋の評価では確認しきれなかった点」「主張の裏取りが必要な点」を優先）
```

## 注意事項

- 行単位のコードレビューはしない。指摘したくなった詳細は「レビューで重点的に見るべき点」に回す
- PR にコメントを投稿したり、PR の状態を変更したりしない（読み取り専用）
- description が空・情報不足でブリーフィングの一部が書けない場合は、そのセクションに「情報なし（diff からの推測のみ）」と正直に書く
- 出力は必ず日本語。技術用語・コード識別子は原語のまま
